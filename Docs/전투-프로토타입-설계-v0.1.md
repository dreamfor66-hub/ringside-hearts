## 1. 왜 만드는가

- 실제 아트와 콘텐츠를 만들기 전에 **전투가 재미있는지** 손으로 확인합니다.
- 범위는 **전투 기획서의 거의 전부**입니다 [확정]. 여러 상황을 직접 겪어 본 뒤, 다음 단계에서 무엇을 고칠지 프로토타입 경험을 근거로 고르기 위해서입니다.
- 그림은 도형이어도 **UI는 정보를 제대로 전달**해야 합니다 [확정]. 왜 다운이 안 됐는지, 지금 누가 무엇을 할 수 있는지가 화면에서 읽혀야 판단을 할 수 있습니다.
- 체크리스트 5장의 원칙(데이터로 캐릭터 추가, 효과 블록)을 프로토타입부터 그대로 씁니다.

## 2. 목표, 안 하는 것, 실패로 보는 것

**목표**
- 매치 선택부터 결과 화면까지 한 판이 끝까지 돌아감
- 전투 기획서 4~12장의 규칙이 들어감 (4장 표 참고)
- 팀 편성과 매치 종류를 바꿔 가며 여러 상황을 볼 수 있음
- 전투 기획서 15장의 확인 항목을 숫자로 기록함 (12장)
- 에디터에서 마우스로, Android 폰에서 터치로 둘 다 플레이 가능

**안 하는 것** (M0 뒤로 미룸, 15장)
- 실제 일러스트, SD, 컷인 그림, 사운드
- 가챠, 성장, 장비, 스토리, 로비, 저장, 서버

**실패로 보는 것** (돌아가도 실패)
- 숫자나 캐릭터별 동작이 코드에 박혀서, 캐릭터 하나 추가하려면 코드를 고쳐야 함
- 화면만 봐서는 결과의 이유를 알 수 없음 (위력이 왜 이만큼인지, 다음 행동까지 몇 턴인지)
- 처음 손에 잡히기까지 너무 오래 걸림. 그래서 단계마다 플레이 가능한 상태로 만듦 (14장)

## 3. 만드는 방법

| | 1. 유니티 물리 | **2. 전투 규칙을 유니티와 분리** | 3. 섞기 |
|---|---|---|---|
| 방식 | 유닛에 Rigidbody2D를 붙이고 규칙도 각 오브젝트에 씀 | 규칙과 단순 원형 물리를 순수 C#으로 따로 만들고, 유니티는 그리기와 입력만 맡음 | 이동은 유니티 물리, 규칙은 순수 C# |
| 장점 | 처음 공이 굴러가기까지 가장 빠름 | 결과가 매번 같음(재현 가능). 화면 없이 수백 판 자동 대전으로 수치 확인. 규칙을 자동 테스트로 검증. 나중에 서버 검증에도 그대로 씀 | 물리를 안 만들어도 됨 |
| 단점 | 뚫고 지나가기, 붙잡아 던지기, 공중 착지 같은 타입 동작이 물리 엔진과 싸움. 재현과 자동 대전이 어려움 | 원과 사각 로프의 충돌을 직접 만들어야 함 (양이 적음) | 재현과 자동 대전 문제가 그대로 남음 |

**2번으로 갑니다** [임의 P2]. 링 안에는 원 2개와 벽 4개뿐이라 물리를 직접 만드는 비용이 작고, 타입 5종의 동작은 어차피 직접 짜야 합니다. 체크리스트 5.5의 "전투 결과 재현"과 15장의 수치 확인도 이 방식에서만 쉽습니다.

### 4.1 같은 캐릭터 구조 [확정, 2026-11-17]
- 캐릭터 데이터, 선수 코드, 팀 코드는 **한 벌**. 내 캐릭터를 그대로 상대 팀에 넣을 수 있고, 반대도 됨
- 두 팀의 차이는 **팀 설정**에만 있음

| 팀 설정 | 값 | 기본 |
|---|---|---|
| 조작 | 사람 / AI | 내 팀 사람, 상대 팀 AI |
| 행동 방식 | 매 턴 / 행동 카운트 N턴마다 | 내 팀 매 턴, 상대 팀 3 |
| 보스 배율 | 스태미나, 파워 배율 | 1 |
| 허용 | 태그, 어필, 개인 필살기, 체인과 합동 필살기, 세컨드 개입 | 모두 켬 |
| AI 정확도 | 오차 각도, 후보 수 | AI일 때만 |

- 상대 팀도 필살기 게이지, 체인, 합동 필살기를 같은 규칙으로 가짐. 실전에서 막고 싶은 콘텐츠가 생기면 그 팀 설정에서 허용만 끔
- AI 대 AI, 사람 대 사람(한 기기)도 팀 설정만 바꾸면 돌아감. 자동 테스트가 이걸 씀

## 5. 판 흐름

### 5.1 내 턴
1. (상대가 다운 중이면) 플랜 선택. 기본은 직전에 고른 플랜, 처음엔 핀폴
2. 태그 (선택, 1회, 턴 소모 없음)
3. 행동 1개: 샷 / 어필 / 필살기 샷(게이지가 찼을 때)
   - 링 안의 내 선수가 다운 중이면 행동은 **버티기**(아무것도 안 함)뿐. 태그로 빼는 것은 가능 [임의 P5]
   - 체인 3칸이 켜져 있고 링 안 선수가 마무리 역할이면, 샷이 자동으로 합동 필살기가 됨
4. 샷 판정 → 다운 또는 피날레 발생 시 처리
5. 턴 끝 처리 (5.2)

### 5.2 턴 끝 처리 순서 [임의 P6]
1. 다운된 선수 회복 (양 팀), 30%에 기상하면 플랜 해제
2. 링 밖 대기 선수 회복 5%
3. 열기 감소 (매 턴 −5, 아무도 못 맞힌 턴 −10 추가, 화려한 플레이 직후 1턴은 감소 없음)
4. 태그 재진입 제한 1턴 감소
5. 상대 행동 카운트 −1. 0이면 상대 행동(5.3) 후 다시 3
6. 턴 수 +1. 20턴을 넘기면 패배

### 5.3 상대 행동 규칙 [임의 P7]
위에서부터 처음 맞는 것을 함.
1. **피날레 시도**: 내 링 안 선수가 다운 중이면. 플랜은 로프 근처면 링아웃(매치가 허용할 때), 링 중앙(중심에서 링 폭의 25% 이내)이면 서브미션, 그 밖에는 핀폴. 내 선수를 향해 직선으로 쏨(오차 ±5°). 닿으면 내가 방어 연타
2. **태그**: 상대 링 안 선수 스태미나가 25% 미만이고, 대기 선수 중 60% 이상인 선수가 있으면 교대한 뒤 3·4로 넘어감
3. **어필**: 상대 열기가 30 미만이고 40% 확률
4. **돌진**: 방향 24개 × 세기 3단계를 시뮬레이션해서 점수(피해 + 다운 보너스 + 라리아트 보너스)가 높은 3개 중 하나를 무작위로 고름. 필살기 게이지가 차 있으면 필살기 샷. 체인이 차 있고 마무리 역할이 링 안에 있으면 내 팀과 같은 규칙으로 합동 필살기
- AI 정확도(오차 각도, 후보 수)는 매치 데이터에서 바꿀 수 있음

### 5.4 피날레
- 내 샷이 다운된 상대에게 닿으면 플랜 실행. 링아웃은 닿은 뒤 그 샷 안에서 상대가 **속도 10 이상**으로 로프에 부딪혀야 실행 [임의 P8]
- 한 샷 안에서 다운이 일어나면, 그 샷의 나머지 타격으로는 플랜이 실행되지 않음 (플랜을 고를 기회가 먼저) [임의 P9]
- 실패하면 상대가 30%까지 회복하고 일어남, 공격 측 열기 +10
- 승리: 상대 한 명에게 피날레 성공. 패배: 내 선수 한 명이 피날레를 당하거나 턴 제한 초과

## 8. 수치 시작값 [임의 P12]

전체 값은 `GameVariables` 에셋(9.1). 판 길이를 정하는 핵심만 적습니다.

| 항목 | 값 |
|---|---|
| 스태미나 | ★3 1000 / ★4 1150 / ★5 1300. 보스는 매치 데이터의 배율 (핸디캡 ×3.5) |
| 파워 | ★3 100 / ★4 115 / ★5 130 |
| 근성 | 캐릭터마다 80~130 |
| 열기 의존 높음 | 쇼메이커 타입 (타이가, 타누, 래프) [임의 P19] |
| 어필 열기 | 쇼메이커 40, 나머지 25~30 |
| 타격 한 번의 피해 | 파워 × 피해 배율(`damage.scale`, 2.4, P23) × 반동 보너스 × 속성 × 열기 × 타입 × 라리아트 × 필살기 배율. 속도는 피해에 영향 없음 (링아웃 판정에만 씀) |
| 다운 회복 | 턴마다 최대치의 (15% + 근성 × 0.03%) |
| 필살기 게이지 | 타격 +20, 로프 반동 +5. 100에서 사용 가능 |
| 개인 필살기 배율 | ×2.5 (캐릭터마다 바꿀 수 있음) |
| 합동 필살기 배율 | ×4 |
| 힘겨루기 시작 위치 | 50 + (열기 − 50) × 0.2 − 상대 남은 스태미나 비율 × 20 |
| 공격 연타 한 번 | +3.5 × (파워 / 100) × 열기 배율(×0.6~1.6) |
| 방어 측 밀어내기 (AI) | 초당 18 × (근성 / 100) × 남은 스태미나 비율 |

목표: 다운까지 내 턴 3~4번, 한 판에 힘겨루기 2~4번, 3~5분 (기획서 15장).

### 8.1 밸런스 목표와 측정 [확정 원칙 2026-11-18, 수치는 임의 P39]
프로토타입은 기능 확인이 아니라 **질 수 있는 게임**으로 넘깁니다 [확정]. 단계마다 봇 대전으로 아래 목표를 확인하고 숫자를 보고합니다.

| 실력 봇 (사람 쪽) | 승률 목표 | 2단계 측정 (100판씩) |
|---|---|---|

## 9. 데이터 구조

### 9.1 파일 [임의 P13]
- 엑셀이나 구글 시트에서 열 수 있는 **CSV** (UTF-8, 한글 깨짐 방지용 BOM 포함)
- 위치: `Assets/Resources/Data/`. 게임 시작 때 읽음. M1에서 원격 배포 구조(체크리스트 5.4)로 옮김

| 파일 | 한 줄 = | 주요 열 |
|---|---|---|
| `characters.csv` | 캐릭터 1명 | 지금(2단계): `id, name, short, attribute, grade, stamina, power, guts, playable`. 추가 예정: 진영, 타입, 체인 역할, 열기 의존(보통/높음), 어필 열기, 필살기 이름, 필살기 배율, 세컨드 스킬(효과 블록) |
| `teams.csv` | 팀 설정 1개 | 지금(2단계): `id, slot1, control(사람/AI), action_every, stamina_mul, power_mul, ai_aim_error, ai_candidates`. 추가 예정: 슬롯 2~3, 세컨드, 허용 플래그. 내 기본 편성도 여기 한 줄 (`player_default`) |
| `matches.csv` | 테스트 매치 1개 | id, 이름, 매치 규칙(효과 블록), 상대 팀 id, 턴 제한 |

물리, 손맛, 링 구조 같은 한 벌짜리 설정값은 CSV가 아니라 **ScriptableObject** `Assets/Resources/Data/GameVariables.asset` 하나에 둡니다 [확정 2026-11-18]. 인스펙터에서 한글 설명과 범위 슬라이더로 고치고, 플레이 중에 고친 값은 다음 샷부터 적용되며 플레이를 끝내도 남습니다. 행이 많은 표(위 세 파일)는 CSV 그대로입니다.

내 팀과 상대 팀이 같은 `teams.csv` 형식이라, 편성 화면에서 만든 팀을 상대 팀 칸에 그대로 넣어 볼 수도 있습니다.

### 9.2 효과 블록 (체크리스트 5.2)
**언제 + 누구에게 + 무엇을**을 셀 하나에 씁니다. 예: `on:partner_causes_down | to:team | heat+10`

| 캐릭터 | 세컨드 스킬 | 효과 블록 |
|---|---|---|
| 블레이즈 레오 | 짝이 다운을 만들면 열기 +10 | `on:partner_causes_down \| to:team \| heat+10` |
| 봄버 타이가 | 짝의 어필 열기 +20% | `always \| to:partner \| appeal_heat*1.2` |
| 스핀캣 루카 | 짝이 어필할 때 열기 +5 | `on:partner_appeal \| to:team \| heat+5` |
| 터스크 | 짝의 최대 스태미나 +5% | `always \| to:partner \| max_stamina*1.05` |
| 토로 그란데 | 장비 효과 +10% | M0에서는 효과 없음 |
| 타누 | 상대 힐 세컨드 개입 효과 절반 | `always \| to:enemy_second \| intervention*0.5` |
| 아이스버그 | 짝의 다운 회복 +15% | `always \| to:partner \| down_recovery*1.15` |
| 스플래시 오티 | 한 판 1회, 못 맞힌 턴의 열기 감소를 막음 | `once:no_hit_turn \| to:team \| cancel_heat_penalty` |
| 제피로 | 짝이 로프에 처음 튕긴 뒤 감속 줄어듦 | `on:partner_first_rope \| to:partner \| friction*0.8` |
| 골든 팽 | 짝의 힘겨루기 시작 위치 +5 | `always \| to:partner \| mash_start+5` |
| 볼트 | 짝의 첫 샷 위력 +15% | `on:partner_first_shot \| to:partner \| power*1.15` |
| 카운터 잭 | 짝의 라리아트 보너스 +10% | `always \| to:partner \| lariat*1.1` |
| 노이르 | 힐 세컨드 개입 시간 +1초 | `always \| to:self \| intervention_time+1` |
| 톡식 래프 | 상대 다운 회복 −10% | `always \| to:enemy_active \| down_recovery*0.9` |
| 데스롤 | 짝의 서브미션에서 상대가 빠져나가기 어려움 | `always \| to:partner \| submission_resist*0.8` |

- 매치 규칙도 같은 방식: 케이지 `always | to:all | ringout_disabled`, 노 로프 브레이크 `always | to:all | rope_break_disabled`, 서브미션 매치 `always | to:all | win_only:submission`
- "언제", "누구에게", "무엇을"의 종류는 코드에 하나씩 등록합니다. 위 조합은 전부 데이터

## 10. 화면과 UI

### 10.1 원칙
- 결과의 이유가 보이게: 피해 숫자 옆에 붙은 배율 태그 (`반동×2`, `속성▲`, `라리아트`, `열기+6%`)
- 지금 할 수 있는 것과 없는 것이 보이게: 태그 잠금, 필살기 게이지, 다운 기상까지 남은 양
- 색은 속성 5색만 씀 (빨강, 파랑, 초록, 노랑, 보라). 나머지는 회색 단계

### 10.2 전투 화면 (세로 1080×1920 기준) [임의 P21]

**링과 에이프런 사방은 어떤 UI도 덮지 않습니다** [확정, 2026-11-17]. 대기 선수는 로프 어느 면에서나 기다릴 수 있으므로(기획서 10장), 화면을 세로로 세 칸으로 나누고 칸끼리 겹치지 않게 합니다.

| 칸 | 높이 (1920 중) | 표시하는 것 |
|---|---|---|
| 상단 | 250 | 턴 수 (5 / 20), 상대 행동까지 남은 턴(큰 숫자), 상대 링 안 선수 카드(이름, 속성색, 타입, 진영, 스태미나 바와 숫자, 필살기 게이지), 상대 체인 3칸(작게), 상대 열기(작게), 매치 규칙, 기록 버튼과 디버그 버튼 |
| 링 | 1080 (정사각형) | 로프 4면 + 사방 에이프런 띠. 링 안 유닛 = 속성색 원 + 이름 두 글자 + 타입 글자, 둘레에 스태미나 고리. 다운이면 회색 + "DOWN" + 기상까지 남은 양. 로프 근처 구역을 옅게 표시 (플랜 판단용). **대기 선수는 에이프런 위에 링 안 유닛의 80% 크기로 서고, 자기 스태미나 고리와 태그 잠금 표시를 직접 달고 있음** (상대 대기 선수 정보를 상단에 따로 두지 않음) |
| 하단 | 590 | 관중 열기 게이지(0/50/100 눈금, 지금 위력 보정 %), 내 체인 3칸, **플랜 선택 줄**, 내 선수 3명 카드(이름, 속성색, 타입, 역할, 스태미나, 필살기 게이지, 세컨드 이름, 태그 잠금. 누르면 태그), 어필 버튼(오를 열기 표시), 필살기 버튼 |

- 화면이 1920보다 긴 폰에서는 남는 높이를 하단 칸에 줌 (엄지가 닿는 쪽)
- 플랜 선택 줄: 상대가 다운 중일 때만 버튼 3개가 켜짐. 평소에는 같은 자리에 "상대가 다운되면 마무리 방식을 고릅니다" 안내. 링 위에 띄우지 않음. 버튼마다 지금 상황의 한 줄 판정 ("로프 근처: 저항 ×1.5", "속도 부족 가능성 높음")
- 링 위에 뜨는 글자(피해 숫자와 배율 태그, "로프 ×2", "라리아트!", "다운!")는 1초 안에 사라지고, 같은 내용이 기록에 남음
- 기록: 상단의 기록 버튼을 누르면 최근 전투 기록 (어떤 샷이 몇 피해, 어떤 배율)

### 10.3 컷인
- 필살기: 화면 가운데 띠에 속성색 판넬 + 이름 + 필살기 이름, 1초
- 합동 필살기: 세 명의 이름 판넬이 차례로, 1.5초
- 피날레: 링 칸을 덮는 컷인. 두 선수를 나란히 두지 않고 **실제 자세처럼 겹쳐서** 보여 줌 [확정, 2026-11-17]. 도형만으로도 상황이 읽히고, 나중에 기획서 16장의 "누르는 포즈와 눌리는 포즈" 그림을 같은 자리에 겹쳐 붙이면 됨 [구도는 임의 P22]

| 플랜 | 구도 (도형) |
|---|---|
| 핀폴 | 방어 측이 컷인 아래쪽에 가로로 누워 깔리고, 공격 측이 그 위에 겹쳐 누름 |
| 서브미션 | 방어 측이 엎드려 누워 있고, 공격 측이 위에서 비스듬히 겹쳐 팔다리를 감음 (팔 모양 선) |
| 링아웃 | 컷인 한쪽에 세로 로프. 방어 측이 로프 너머로 반쯤 넘어가게 기울고, 공격 측이 링 안쪽에서 겹쳐 밀어붙임 |

- 도형 한 명 = 몸통(둥근 사각형) + 머리(원). 머리 방향으로 누웠는지 섰는지가 보이게 함
- 연타가 진행되면 구도가 같이 움직임: 핀폴은 게이지에 따라 방어 측 어깨가 들림, 링아웃은 게이지에 따라 로프 밖으로 더 넘어감

### 10.4 연타 힘겨루기 (아래쪽 1/3)
| 플랜 | 입력 (폰) | 입력 (PC) | 화면 |
|---|---|---|---|
| 핀폴 | 아무 곳이나 연타 | 클릭 또는 스페이스 연타 | 게이지와 60 눈금, 카운트 "1… 2…" |

| 링아웃 | 누르고 있다가 신호가 뜨면 연타 | 스페이스를 누르고 있다가 신호에 연타 | 게이지, 신호 표시. 신호 전에 떼면 게이지 −10 [임의 P15] |

- 세컨드 개입 버튼: 오른쪽 아래. 이번 판에 썼으면 회색

### 10.5 전투 밖 화면 (최소)

## 13. 코드 구조

```
Assets/Game/
  Battle/Core/     순수 C#. 유니티를 참조하지 않음 (규칙, 물리, AI, 효과 블록, 연타 판정)
  Battle/View/     유니티. 링 그리기, 입력, UI, 컷인
  Data/            CSV 읽기 → 데이터 객체
  Prototype/       매치 선택, 편성, 결과, 디버그 메뉴
Assets/Resources/Data/   CSV
Assets/Scenes/BattlePrototype.unity
Assets/Tests/EditMode/   규칙 자동 테스트
```

- 샷은 Core가 한 번에 끝까지 계산해서 "궤적 + 일어난 일 목록"을 돌려주고, View가 그걸 재생합니다. 그래서 조준 가이드, 상대 AI, 자동 대전이 같은 계산을 씁니다
- 연타 힘겨루기는 Core가 시간과 입력을 받아 판정합니다
- 난수는 시드를 정해서 씀. 같은 시드와 같은 입력이면 같은 결과
- 자동 테스트: 반사 각도, 피해 계산, 다운과 기상, 태그 규칙, 플랜 실행 조건, 타입 5종, 효과 블록, 승패, AI끼리 한 판이 끝까지 가는지
